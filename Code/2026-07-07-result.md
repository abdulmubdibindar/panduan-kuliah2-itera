# Ringkasan Hasil - 2026-07-07

Catatan sesi debugging 403 pada [[method_claude.py]], ditulis supaya bisa dilanjutkan dari komputer lain.

## Kronologi Masalah

1. Skrip dijalankan dengan `--cookie-file cookie.txt --user-agent "..."` (UA disamakan dengan `navigator.userAgent` browser), tetap 403.
2. **Penyebab #1 (ditemukan & DIPERBAIKI):** isi `cookie.txt` cuma berisi **nilai** `cf_clearance` tanpa prefix nama, contoh:
   ```
   TL3gPHQNuTxmbyqt7BePNkM8IXO8rABDdH...
   ```
   Padahal `build_session()` di [[method_claude.py]] mem-parsing dengan mencari tanda `=` (format yang benar: `cf_clearance=<nilai>`). Tanpa `=`, kondisi `if "=" in pair` gagal untuk seluruh isi, sehingga **tidak ada cookie yang benar-benar terpasang** ke session — request dikirim tanpa `cf_clearance` sama sekali.
   - **Perbaikan**: `cookie.txt` ditambahkan prefix `cf_clearance=`.
   - **Perkuatan skrip**: `build_session()` sekarang mencetak `PERINGATAN` ke stderr kalau string cookie diberikan tapi tidak ada pasangan `nama=nilai` yang berhasil di-parse (`session.cookies` kosong setelah loop).
3. Setelah format cookie diperbaiki, skrip **masih 403**. Ditambahkan debug print sementara di `api_get()` untuk mencetak header respons (`Cf-Ray`, `Cf-Mitigated`, `Server`) + cuplikan body saat 403.
4. Hasil debug:
   ```
   Cf-Mitigated: challenge
   Server: cloudflare
   body: "<title> Moodle challenge </title>" ... (halaman interstisial standar)
   ```
   **`Cf-Mitigated: challenge`** artinya Cloudflare secara aktif menantang ulang request ini — bukan sekadar menolak cookie basi. Ini terjadi walau cookie `cf_clearance` dan `User-Agent` sudah persis sama dengan yang dipakai browser saat lolos challenge.

## Diagnosis

Karena cookie + UA sudah cocok tapi tetap ditantang, kemungkinan besar penyebabnya adalah **fingerprint di lapisan TLS (JA3/JA4)**: pustaka `requests`/urllib3 Python melakukan TLS handshake dengan urutan cipher-suite, ekstensi, dan ALPN yang berbeda dari Chrome/Edge asli — walau header HTTP-nya (UA, cookie) dibuat identik. Cloudflare Bot Management memakai fingerprint tingkat-TLS ini sebagai sinyal utama, dan ini **tidak bisa diperbaiki hanya dengan mengatur header**, karena terjadi sebelum lapisan HTTP terbentuk.

Temuan ini konsisten dengan risiko yang sudah diperkirakan sejak awal proyek di [[SARAN_AGY.md]] poin 1 ("Playwright atau crawler headless standar sering kali diblokir oleh Cloudflare karena tanda tangan browser otomatis terdeteksi").

## Opsi Langkah Selanjutnya (belum diputuskan)

**Opsi A — `curl_cffi` (perubahan kecil, cepat dicoba)**
- Ganti `requests.Session()` di `build_session()` dengan `curl_cffi.requests.Session(impersonate="chrome124")` (atau versi Chrome terbaru yang didukung).
- Cukup `pip install curl_cffi`; sisa kode (parsing JSON, loop halaman, dsb.) tidak perlu berubah karena `curl_cffi` API-compatible dengan `requests`.
- Kalau berhasil, tidak perlu membuka Chrome sama sekali saat menjalankan skrip.

**Opsi B — Remote debugging Chrome (CDP), sesuai usulan asli [[SARAN_AGY.md]]**
- Jalankan Chrome dengan `--remote-debugging-port=9222 --user-data-dir=...`, selesaikan challenge manual sekali di jendela itu.
- Skrip terhubung ke sesi Chrome asli itu via Playwright (`connect_over_cdp`) — traffic betul-betul lewat browser asli sehingga TLS fingerprint otomatis valid, cookie juga otomatis terbawa (tidak perlu copy-paste `cf_clearance` lagi).
- Paling andal, tapi perlu instal Playwright + Chrome harus tetap terbuka selama skrip jalan, dan bagian pengambilan data (`fetch_page_html`, `list_all_pages`) perlu ditulis ulang memakai `page.evaluate()`/`fetch()` alih-alih `requests.get()`.

**Rekomendasi bila harus memilih satu**: coba Opsi A dulu (perubahan minimal, cepat diuji) karena kalau berhasil sisa arsitektur skrip (MediaWiki API, unduh gambar, tulis ulang tautan, pandoc) tidak perlu dibongkar. Kalau `curl_cffi` juga masih kena tantang, baru pindah ke Opsi B.

## Status Berkas Saat Ini

- [[cookie.txt]]: sudah diperbaiki formatnya (`cf_clearance=<nilai>`), tapi **nilai cookie di dalamnya kemungkinan sudah dianggap "tertantang" oleh Cloudflare** (mendapat halaman challenge, bukan expired murni) — sebaiknya ambil cookie segar lagi saat melanjutkan.
